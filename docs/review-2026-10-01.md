# Proxy review: 2026-10-01

A review of `main` and the two open PRs against Claude Code 2.1.286 and the
live GitHub Copilot API. It covers the issues raised in earlier sessions: new
model support, the context-window display, the web search limit in dynamic
workflows, and retries of LLM calls. It also covers the auto mode notice that
Claude Code shows behind the proxy.

**Scope:** `main` at `015d83c`, PR #10 (`fix/copilot-split-choices`), and PR #8
(`fix/native-gateway-reliability`).

**Method:** reading the code, running the test suites, and running live checks.
The live checks used about forty small Copilot requests. Claude Code's
outgoing requests were captured by pointing it at a local recorder that never
forwards anything upstream.

## How to read the findings

Each finding lists what was observed, the evidence, and the fix. Where a
finding depends on Claude Code's behavior, the evidence is either Claude Code's
documentation, a request captured from Claude Code 2.1.286, or strings in the
2.1.286 binary.

## 1. Split non-streaming choices drop tool calls

**Observed:** For Claude models, Copilot's non-streaming Chat Completions
response splits one assistant turn across choices: the text in one choice and
each tool call in its own. `main` read only `choices[0]`, so it dropped every
tool call but still reported `stop_reason: tool_use`. Claude Code then failed
with "The model's tool call could not be parsed (retry also failed)."

**Evidence:** A live non-streaming request asking for text plus two tool calls
returned three choices, all with `finish_reason: tool_calls`. Streaming
responses are not split. This session hit the bug at 11:29 local time, before
the proxy was restarted on #10.

**Why it ran at all:** Claude Code falls back to a non-streaming request when a
stream stalls. Copilot streams Claude's thinking as `reasoning_text` deltas,
which the proxy did not forward, so long thinking left the stream silent and
Claude Code's stall watchdog fired.

**Fix:** #10 combines all choices and sends keep-alive `ping` events after 15
seconds without output. Merged as `ed0e1b4`.

## 2. Auto mode `safeguards` field

**Observed:** In auto mode, Claude Code 2.1.286 adds a top-level `safeguards`
field and the `dangerous-tool-use-2026-09-03` beta to ask the server to run the
permission classifier. Copilot rejects the field on its native Messages
endpoint:

```text
400 invalid_request_error: safeguards: Extra inputs are not permitted
```

`main` drops the field when translating to Chat Completions, so no verdicts
come back. Claude Code falls back to its own classifier requests and shows the
"isn't eligible" notice. PR #8 forwards the field unchanged and gets the 400.
Claude Code then retries once without the field, so each session wastes one
request.

**Evidence:** Captured requests show the field on the first request of an auto
mode session, then a retry without it. With `CLAUDE_CODE_AUTO_MODE_SERVER=0`,
Claude Code never sends it.

**Not fixable in the proxy:** Only Anthropic's API produces classifier verdicts.
Fabricating `safeguard_results` would forge safety verdicts.

**Fix:**

- Users set `CLAUDE_CODE_AUTO_MODE_SERVER=0`. `scripts/launch.sh` does this
  since #10.
- The proxy strips `safeguards` and the `dangerous-tool-use-*` beta on the
  native transport, so a session without the variable still works and doesn't
  pay for a failed request. Claude Code then falls back to its own classifier,
  as it does today.

## 3. Model routing

**Observed on `main`:**

| Claude Code sends | `main` routes to | Copilot |
|---|---|---|
| `claude-opus-5-5` (opus) | `claude-opus-5.5` | Available |
| `claude-sonnet-5-5` (sonnet) | `claude-sonnet-5` | Downgraded, though 5.5 is available |
| `claude-haiku-4-5-20251001` (haiku) | `claude-haiku-4.5` | Available |
| Sonnet 4.x, Opus 4.6 and older, or no model | `claude-sonnet-4.6` / `claude-opus-4.6` | Retired: `400 model_not_supported` |

`/v1/models` on `main` still advertises the two retired models and omits Sonnet
5.5. The model map is maintained by hand, and the tests only check that IDs
have the right shape, not that Copilot still offers them. Every catalog change
has needed a new PR.

**Fix:** #8 resolves IDs against Copilot's live `/models` catalog and never
substitutes a version. It routes both 5.5 models correctly.

## 4. Context-window display

**What works:** Copilot sends `usage` on the same chunk as `finish_reason`, and
the proxy reads it before closing the message, so the context display is
correct after each response. Cached tokens come through. Copilot's context
windows match what Claude Code assumes for these model IDs: 1M for Opus 4.7 and
later and Sonnet 5 and later, 200K for Haiku 4.5. No override is needed.

**What was wrong on `main`:** `/v1/messages/count_tokens` used a character
estimate that undercounts:

| Input | Copilot count (Opus 5.5) | `main` estimate | Ratio |
|---|---|---|---|
| 68 KB of JavaScript | 27,378 | 16,577 | 0.61 |
| Tool schema plus tool result | 9,382 | 5,305 | 0.57 |

Opus 5.5 counts about 29% more tokens than Haiku 4.5 for the same text, so no
fixed characters-per-token ratio can be right.

**Fix:** #8 forwards `count_tokens` to Copilot's native endpoint, which returns
exact counts.

## 5. Prompt-too-long error

**Observed:** Copilot returns:

```json
{"error":{"code":"model_max_prompt_tokens_exceeded","message":"prompt is too long: 233656 tokens > 200000 maximum","type":"invalid_request_error"},"type":"error"}
```

`main` wrapped that whole body as a string inside its own `api_error`. Claude
Code still recognized "prompt is too long" and compacted. But the JSON-escaped
`>` stopped it from reading the token counts in the message.

**Fix:** #8 passes the native error envelope through.

## 6. WebSearch fails on Opus 5.5 and Sonnet 5.5 (PR #8)

**Observed:** Claude Code's WebSearch tool makes a nested request with the
`web_search_20250305` server tool. On Claude Code 2.1.286, that request's shape
depends on how the model ID is spelled:

| `--model` | Nested request sends |
|---|---|
| `opus`, `sonnet`, `claude-opus-5-5`, `claude-sonnet-5-5` | `tool_choice: {type: "auto"}`, no `thinking` field |
| `claude-opus-5.5`, `claude-sonnet-5.5` (Copilot's dotted IDs) | `tool_choice: {type: "tool", name: "web_search"}`, `thinking: {type: "disabled"}` |
| Opus 5, Sonnet 5, Haiku 4.5 | `tool_choice: {type: "tool", name: "web_search"}`, `thinking: {type: "disabled"}` |

Claude Code recognizes the dashed IDs as 5.5 models and adapts. It treats the
dotted IDs as unknown models and sends the older shape. Copilot rejects that
shape for 5.5 models on both endpoints:

| Copilot model | Forced `tool_choice` | `thinking: {type: "disabled"}` |
|---|---|---|
| `claude-opus-5.5`, `claude-sonnet-5.5` | `400 tool_choice: type "tool" and "any" are not supported for this model.` | `400` (use adaptive thinking, or `between_tools` on Sonnet 5.5) |
| `claude-opus-5`, `claude-sonnet-5`, `claude-opus-4.8`, `claude-haiku-4.5` | Accepted | Accepted |

So WebSearch fails with a 400 whenever a 5.5 model is selected by its Copilot
ID. That includes the IDs that PR #8's `/v1/models` advertises and that its
README tells users to pick. PR #8 forwards both fields unchanged. An in-process
test confirmed the forced choice reaches Copilot unchanged.

With `tool_choice: auto` and no `thinking` field, both 5.5 models still call
`web_search` for the WebSearch prompt, which is what Claude Code itself does for
the dashed IDs.

**Fix:** For models whose catalog entry advertises adaptive thinking but no
manual thinking budget, the proxy:

- downgrades a forced `tool_choice` to `auto` before sending it upstream; and
- drops `thinking: {type: "disabled"}`.

Both changes apply to the search emulation and to ordinary requests. If the
model still answers without calling the forced tool, the response stands, the
same as when Claude Code sends `auto` itself.

## 7. Web search limits in workflows

There are two separate limits.

**Claude Code's session budget:** each session gets 200 WebSearch calls, and
every agent in the session shares that counter. When it runs out, searches
return "this session has used its web search budget (200 of 200 WebSearch
calls)". The proxy cannot change this. Raise it with
`CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION` in the `env` block of
`~/.claude/settings.json`. Each search costs several model calls through the
proxy, so a higher cap uses more Copilot quota.

**Proxy-side failures on `main`:**

- When the model writes text before calling the search tool, Copilot splits
  the text and the tool call into separate choices (finding 1). `main` read
  only the text, so the search returned nothing. Fixed by #10.
- Brave, Serper, and DuckDuckGo requests had no timeout. With only two search
  slots, one stuck provider blocked every agent's searches.
- Nothing reached Claude Code until the whole search loop finished. Long loops
  could run past Claude Code's request timeout, and each retry re-ran the whole
  loop.
- When every provider failed, the proxy returned an empty result list rather
  than an error. The model then searched again, burning the budget faster.
- `allowed_domains` and `blocked_domains` were read but never applied.

**Fix:** #8 bounds every provider request with a timeout, streams progress
during the loop, returns `web_search_tool_result_error` when providers fail,
and enforces domain filters.

## 8. Non-streaming header timeout

**Observed:** `main`'s 120 second timeout covers the wait for response headers.
In non-streaming mode, Copilot sends headers only when the reply is finished:
a 1,572-token reply took 19 seconds before any header arrived. A reply longer
than 120 seconds was aborted and regenerated, up to three more times, before a
504. A test with the timeout set to 8 seconds reproduced this: two finished
generations were thrown away, then the client got a 504.

Every web search round and Claude Code's non-streaming fallback use this path.

**Fix:** #8 stops replaying ambiguous failures and treats the timeout as an
idle timeout on body reads.

## 9. Retry multiplication

**Observed:** The proxy retries up to four times, and Claude Code retries up to
eleven, so one request can reach Copilot up to forty-four times. `main` doesn't
pass `retry-after` or `x-should-retry` back, so Claude Code can't tell a
temporary throttle from a final error.

**Status:** #8 bounds this well:

- It retries only explicit HTTP statuses (429, 500, 502, 503, 504), never
  ambiguous network failures that may already have run a completion.
- All attempts share a 30 second budget (`COPILOT_RETRY_BUDGET_MS`).
- It never retries past an upstream `retry-after`. When the hint exceeds the
  budget, it returns the 429 at once with the header intact.
- Upstream response headers, including `retry-after` and `x-should-retry`, pass
  through to Claude Code.

Copilot's retry headers reach Claude Code, so its retry layer can decide. What
remains is up to 30 extra seconds before Claude Code sees a persistent 5xx.
That's a tuning trade-off rather than a bug. To leave retries to Claude Code
alone, set `COPILOT_MAX_RETRIES=0`.

## 10. Broken stream reported as a clean finish

**Observed:** When the upstream stream broke, `main` closed every open block and
sent `stop_reason: end_turn`. Claude Code accepted a cut-off answer as complete,
and a half-streamed tool call arrived as invalid JSON. Claude Code expects an
error in this case, so it can retry or show "The response above may be
incomplete."

**Fix:** #8 reports the failure as an error event instead of a terminator.

## 11. Client cancellation

**Observed:** When Claude Code cancels a request (Esc, a stall, or a retry),
`main` kept reading Copilot's stream to the end. A test client that hung up
after 2.5 seconds still produced "stream complete" in the proxy log. In
workflows with many agents, this wastes quota and adds to rate limiting.

**Fix:** #8 aborts the upstream request when the client disconnects.

## 12. Network exposure

**Observed:** `main` listens on all interfaces with no authentication and
`Access-Control-Allow-Origin: *`. On the review machine it answered on the LAN
address, the network profile was Public, and Windows Firewall allowed inbound
connections to `node.exe`. Anyone on that network, or any web page in a
browser on the machine, could spend the account's Copilot quota.

**Fix:** #8 binds to `127.0.0.1`, requires a local API key, and drops CORS.

## 13. Flaky OAuth tests

**Observed:** Five `test-auth.mjs` cases ("new OAuth grant is already persisted
when Copilot returns HTTP …") failed on PR #8's unmodified head. They fail
because the test fixture uses a fake clock for sleeps but a real 100 ms timer
for request deadlines. A loaded machine can take longer than that between the
credential write and the `/models` reply, so the request times out and the
test sees `unavailable` instead of the HTTP status.

**Fix:** Give the fixture a deadline that real I/O can't exceed by accident.

## 14. Dotted model IDs (PR #8)

**Observed:** PR #8's `/v1/models` returned Copilot's dotted IDs, such as
`claude-opus-4.7`, and its README tells users to pick from that list. Claude
Code recognizes only the dashed Claude API spelling. For an unknown ID it
assumes a 200K window and a 32K output limit. Claude Code's own model usage
report for one request per spelling:

| Model ID | Context window | Max output tokens |
|---|---|---|
| `claude-opus-5-5` | 1,000,000 | 128,000 |
| `claude-opus-5.5` | 1,000,000 | 64,000 |
| `claude-opus-4-7` | 1,000,000 | 64,000 |
| `claude-opus-4.7` | 200,000 | 32,000 |
| `claude-haiku-4-5` or `claude-haiku-4.5` | 200,000 | 32,000 |

So a session on `claude-opus-4.7` compacted at a fifth of its real window. The
dotted 5.5 IDs keep their window by coincidence, but get the pre-5.5 request
shape from finding 6.

**Fix:** `/v1/models` advertises the dashed spelling, with Copilot's readable
name as `display_name`. The proxy maps it back to the same catalog entry, so
dotted IDs keep working when typed.

## 15. Windows credential replacement

**Observed:** `savePrivateJson` writes credentials atomically by renaming a
temporary file over the target. On Windows, that rename fails with `EPERM`
while another process has the target open. The code retried for two seconds.
Measured with a reader looping on the target: the rename stayed blocked for a
median of 0.5 seconds, p90 2.6 seconds and at most 2.9 seconds, so about one
write in eight failed. "readers never observe partial JSON during
replacements" failed intermittently for this reason.

**Fix:** Retry for up to ten seconds. The write stays atomic, and only sharing
errors are retried.

## Recommended settings

Put these in the `env` block of `~/.claude/settings.json` so they also reach
background agents and terminals that are already open:

```json
{
  "env": {
    "CLAUDE_CODE_AUTO_MODE_SERVER": "0",
    "CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION": "400"
  }
}
```

Raise the search budget only if workflows actually reach 200 searches; each
search uses Copilot quota.
